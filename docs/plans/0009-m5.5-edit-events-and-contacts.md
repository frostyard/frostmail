# Plan 0009: M5.5 edit events and contacts

M5.5 makes Frostmail's Calendar and People writable. Today the user can
answer invitations, add a sender to Contacts and edit tasks, but cannot
create, change or delete an event or a contact. This milestone adds both:
an event editor window, direct manipulation in the day, week and month
views, recurring edits, invitations to events the user organizes, an edit
mode for contacts with photos, and undo for all of it. It follows
[M5](0008-m5-mail-app-parity.md) and comes before M6 (packaging) in the
[roadmap](0002-roadmap.md), so the first installs can edit. Managing
calendars and address books themselves stays Later.

## Decisions for M5.5

Phase 1 records these as ADRs 0030–0034. The user chose the scope on
2026-10-14: invitations are in, and so are dragging, undo and contact
photos. The same day, the user chose that Frostmail asks before telling
invitees.

- **Every edit is a patch** ([ADR-0018](../adr/0018-keep-contacts-events-and-tasks-as-sent.md)).
  An event change rewrites only the properties it touches, in the object
  as the server sent it (`calendar.PatchEvent`, `calendar.NewEvent`); a
  contact change does the same in the card's own vCard version, keeping
  Apple's grouped labels (`item1.EMAIL` with `item1.X-ABLabel`), vendor
  properties and parameters (`vcardx.Patch`, `vcardx.NewCard`). Each
  function has golden tests over Google's, iCloud's and Nextcloud's
  sources.
- **A refused write is re-applied.** The design now fails a write the
  server refuses with 412 for good, and the server's version stands.
  For an edit, that loses the user's change without a word. Instead,
  maild refetches the object and applies the same change again when the
  properties it touches are as they were when the change was made. When
  another client changed them too, the server's version stands and the
  app says so.
- **The event editor is its own window**
  ([ADR-0020](../adr/0020-one-window-for-mail-calendar-people-and-tasks.md)),
  as compose is. It opens from New Event, a double-click or Enter on an
  occurrence, and the event pane's Edit. Quick changes happen in place:
  drag an occurrence to move it, drag its edge to change its length, drag
  across empty time to create one, and press Delete to delete.
- **Recurring edits have three scopes.** This Event writes an override
  (a VEVENT with `RECURRENCE-ID`) into the series' object, or deletes the
  occurrence with an `EXDATE`. All Future Events ends the series with
  `UNTIL` before the occurrence and starts a new series, under a new UID,
  from it. All Events patches the master. Phase 1's ADR decides what
  happens to overrides when All Events moves the time.
- **New events are in the app's time zone.** The event carries the IANA
  `TZID` and a `VTIMEZONE` that maild generates from its built-in tzdata,
  with golden tests. All-day events are dates.
- **Invitations follow ADR-0022's rule** for events the user organizes.
  An event with invitees goes out through the server's scheduling only
  where the provider is verified to tell invitees about events a client
  writes (a new provider fact). Anywhere else, maild mails the iTIP
  `REQUEST` or `CANCEL` through the outbox with its undo delay, and the
  event's `ATTENDEE` lines carry `SCHEDULE-AGENT=CLIENT` so the server
  sends no second copy. A change to the time, place or recurrence raises
  `SEQUENCE` and tells the invitees. Removing an invitee or deleting the
  event cancels it for them. Invited events (where the user is not the
  organizer) stay answer-only, apart from the user's own alerts.
- **Undo restores what a change replaced**
  ([ADR-0032](../adr/0032-undo-restores-what-a-change-replaced.md)).
  Every write keeps, for a day, the sources it replaced and returns a
  `restoreId`. The app's undo list holds `calendar.restore` or
  `people.restore` with it, as Mail's holds its inverse calls
  ([ADR-0028](../adr/0028-mute-and-block-in-maild-undo-in-the-app.md)), so
  edits, deletes, splits and moves all undo the same way. Undoing a change
  that told invitees asks again.
- **Contact photos are scaled in the app.** The app reads an image file
  the user picks, crops it square, and scales it to at most 512 × 512 JPEG
  on a canvas. maild checks the type and size (at most 256 KB) and writes
  `PHOTO` in the card's version. Nothing is fetched.
- **Moving an event between calendars** writes it to the new calendar and
  deletes it from the old one, on the same account or another. An event
  with invitees moves only within its account, so its organizer stays the
  same.
- **Deleting is confirmed** for contacts, and for events with invitees,
  since both are permanent on the server once the undo window has passed.

## Phase 2 — Contacts — done

- Planner: the 412 re-application in `pimsync` (shared with Phase 3);
  `people.create`, `update`, `delete` and `restore` as `put` and `delete`
  ops; `people.setPhoto`.
- Planner, first: the `pim_restores` migration, and the people writes
  over `vcardx.Patch` and `NewCard` (T-0132, T-0133) in place of
  `edits.go`'s stubs.
- Cards, in order, each merged before the next: T-0132 and T-0133 (the
  vCard patches), T-0134 (MockTransport's contact edits), T-0135 (the
  editor and its draft), T-0136 (editing from the person pane, New
  Contact, Ctrl+N), T-0137 (photos, Delete Contact, refused changes),
  then T-0138 (`mailctl people add/edit/rm`).
- **Done when:** on the throwaway Gmail account and the iCloud account, a
  contact created, edited in every field kind, given a photo and deleted
  in Frostmail shows the same in Google Contacts and on iCloud.com. The
  stored source differs from the server's only on the edited lines, a
  card edited elsewhere meanwhile is re-applied or left as the ADR says,
  and verify is clean.
- **Evidence so far (2026-10-14):** the planner's people writes over
  `vcardx.Patch` and `NewCard`, the `pim_restores` migration (0015), and
  the 412 re-application in `pimsync` (`reapply.go`). The tests cover:
  - writes, extended puts, photos, creates, deletes and restores
    (`TestContactEditsReachTheServer`, `TestContactCreateAndDelete`,
    `TestContactRestore`);
  - an edit applied again over another client's change to another field
    (`TestContactEditAppliedAgainAfterAnotherClient`);
  - refusals for the same field, a contact deleted elsewhere, and a
    delete on an old ETag (`TestContactEditRefusedWhenTheFieldChanged`,
    `TestContactEditOfAContactDeletedElsewhere`,
    `TestContactDeleteRefusedAfterAnotherClient`);
  - day-old restores dropped, and invalid input refused
    (`TestRestoresLastADay`, `TestContactWritesRefuseWhatCannotBeWritten`).

  Against Radicale in the test container, `TestRadicaleContactEdits` (make
  engine-it) does the same round trip with a clean verify. Cards T-0132
  to T-0138 each verified on Codex's first attempt and were merged in
  order, each before the next started.
- **On the user's accounts (2026-10-14),** with maild 489cec2 installed:
  a throwaway contact went through every step on the throwaway Gmail
  account and on the iCloud account, and was read back from maild's copy
  after a later pass took the server's:
  - created, then edited in every field kind (names, nickname, company,
    title, two labeled emails including a custom label, two phones, an
    address, a URL, a birthday, a two-line note);
  - given a 512 × 512 JPEG (13,497 bytes);
  - deleted, restored, and deleted again.

  Both servers kept every field and the photo as written, and verify
  was clean on both (iCloud: 420 contacts on each side).
- **Found and fixed on the way:**
  - `contentline.Apply` refused an insertion at the offset where a
    rewritten line started (a new email before a changed NOTE);
  - Google refuses to re-create a contact at its deleted name, so a
    restore of a written delete now uses a new name (design/pim.md,
    Editing).

  Another client's edit meanwhile was shown on Radicale
  (`TestRadicaleContactEdits`), not on the user's accounts; the week of
  Phase 6 meets it there.

## Phase 3 — Events

- Planner: `calendar.create`, `update`, `delete` and `restore` as ops,
  with the instances re-expanded at once so the views move before the
  server answers; the three scopes; moves between calendars; the
  `VTIMEZONE` generator.
- Cards: `calendar.PatchEvent` and `calendar.NewEvent` with golden tests,
  the scopes' writes included; the repeat rules the editor offers (none,
  daily, weekdays, weekly on chosen days, monthly, yearly, every N, ending
  never, on a date or after a count) to and from `RRULE`; the event editor
  window (title, location, all-day, start and end with the zone, repeat,
  calendar, alerts, availability, notes); the scope sheet; the event
  pane's Edit and Delete; New Event in the Calendar toolbar and Ctrl+N;
  MockTransport's calendar writes; `mailctl cal add/rm`.
- **Done when:** on the throwaway Gmail account and the iCloud account,
  a timed, an all-day and a recurring event created in Frostmail look the
  same in Google Calendar and on iCloud.com. Each scope of an edit and a
  delete gives the occurrences the other client shows, a move between
  calendars leaves one copy, unknown properties survive, alerts fire, and
  verify is clean.

## Phase 4 — Dragging and undo

- Cards: in the day and week views, dragging an occurrence moves it in
  15-minute steps, dragging its bottom edge changes its end, and dragging
  across empty time creates an event and opens the editor. In the month
  view and the all-day strip, dragging moves an occurrence by days. A
  recurring occurrence asks for its scope when dropped. Delete removes the
  selected occurrence. Ctrl+Z undoes event and contact edits, deletes
  (through `restore`) and moves, as Mail's undo does.
- **Done when:** each drag writes one change that the other client shows,
  Escape during a drag changes nothing, and Ctrl+Z after every kind of
  edit and delete brings the earlier event or contact back on the server.

## Phase 5 — Invitations

- Planner: the iTIP `REQUEST` and `CANCEL` builders (`internal/itip`),
  with golden tests; which changes raise `SEQUENCE`; the per-provider
  rule; invitees added, removed and changed through each scope; the new
  provider fact, verified on Google and iCloud and recorded in their
  profiles.
- Cards: the editor's Invitees field (address completion with contacts
  first, as compose's), each invitee's answer and an optional mark; the
  confirmations before an update or cancellation goes out.
- **Done when:** for an event the user organizes on Google and on iCloud,
  with an invitee on Google, one on iCloud and one elsewhere, each
  invitee gets exactly one invitation, one update after a time change and
  one cancellation after a delete, and their answers show in Frostmail.

## Phase 6 — On the user's accounts

- The editing flows on the user's real Gmail and iCloud accounts, verify
  daily. Write sessions on the throwaway account are recorded with
  `MAILD_DAV_TRACE`, scrubbed by `tools/davrec`, and become replay tests.
- **Done when:** the user has edited their own events and contacts in
  Frostmail for a week with verify clean, and Google's and iCloud's write
  sessions replay in `make check`.

## Later / ideas

- Managing calendars and address books: create, rename, recolor and
  delete them (`MKCALENDAR`, `MKCOL`, `PROPPATCH`).
- Contact groups (Apple's group vCards); linking and merging cards;
  Google's other contacts through the People API.
- Free/busy and a scheduling assistant; proposing new times (`COUNTER`);
  delegating.
- Quick entry ("Lunch with Ann tomorrow at noon"); attachments on events;
  the Google Calendar API's extras (Meet links, working location, focus
  time).
- Calendar in its own window; two calendars side by side.

## Open questions

- **Do Google and iCloud tell invitees about an event a client writes
  over CalDAV?** Decided by Phase 5 on the throwaway and real accounts;
  until then, maild mails.
- **Do the servers take Frostmail's `VTIMEZONE`, or keep their own?**
  Decided by Phase 3.
